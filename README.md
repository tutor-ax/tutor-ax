# tutor-ax

기존 학원 HTML 서비스의 디자인과 업무 규칙을 유지하는 React 마이그레이션 작업본입니다.

> **현재는 합성 데이터 전용 개발본입니다. 운영 로그인·DB·SMS와 연결되어 있지 않습니다.**
> 고객 저장소와 운영 사이트는 변경하지 않습니다. 이 저장소는 Private으로 유지합니다.

## 현재 범위

| 영역 | 상태 |
| --- | --- |
| React + TypeScript + Vite 공통 기반 | 구현 |
| 성적 확인 화면 | 데모 데이터로 구현·테스트 |
| 주간/모의고사 선택, 동적 채점 항목, 재시험, 결석, 과제, 클리닉 메모 | 구현 |
| 평균·석차·누적 평균·최고 점수·Chart.js 추이 | 구현 |
| 데모 세션 유지·로그아웃·브라우저 뒤로 가기 | 구현 (실제 인증 아님) |
| 운영 로그인·서버 세션·실제 데이터 조회 | 미연결 — 별도 테스트 백엔드 확인 필요 |
| 관리자 | 반·학생·주차·점수·모의고사·출석·클리닉·메모·문자 미리보기·복원 데모 |
| 단어 공부 | 범위 선택·카드·퀴즈·즐겨찾기·오답노트 (고정 데모 정답) |
| 지문 공부 | 그룹/지문 선택·문장별 해석·전체 해석·단어·이전/다음 |
| OCR·RAG·클리닉 에이전트 | 아직 구현하지 않음 |

## 공개 데모

https://yooncandooit.github.io/tutor-ax/

관리자: https://yooncandooit.github.io/tutor-ax/admin/ (학생 로그인 없이 합성 데이터만 표시)

요청받은 학원 로고는 공통 헤더에 포함했습니다. 관리자 변경은 브라우저별 샘플에만 저장되며 학생 성적 확인의 고정 fixture와 연동되지 않습니다.

main에 push하면 `.github/workflows/pages.yml`이 합성 데이터 전용 앱을 빌드하고 `dist`만 GitHub Pages에 배포합니다. 저장소는 Private이지만 이 데모와 배포된 JavaScript는 공개입니다. 고객 학원명은 데모 표기로 변경했습니다. 실제 고객 데이터·서버 자격증명은 포함하지 않습니다.

Pages 빌드는 `PAGES_BUILD=true npm run build`를 사용합니다. `/tutor-ax/` asset base와 hash 경로를 사용해 탭 이동 후 새로고침도 유지합니다. 원본 비교용 HTML과 문서는 배포하지 않습니다.

## 실행

Node.js 22와 npm 10.9 이상을 권장합니다. 로컬 검증은 Node 20.12.2에서도 수행했습니다. `.nvmrc`는 프로젝트용 권장 버전이며 시스템 Node를 자동 변경하지 않습니다.

```sh
npm ci
npm run dev
```

http://127.0.0.1:5173 에서 **데모로 둘러보기**를 누릅니다. 실제 학생 이름이나 PIN을 입력할 필요가 없습니다. 기존 로그인 폼은 디자인 보존용이며 운영 인증을 수행하지 않습니다.

빌드된 결과 확인:

```sh
npm run build
npm run preview
```

http://127.0.0.1:4173

브라우저 데이터 통신은 기본 차단합니다. 개발 서버에서만 로컬 Vite HMR WebSocket을 허용합니다. Google Fonts는 기존 디자인 유지를 위해 스타일·폰트 요청만 허용하며, 인터넷이 없으면 시스템 글꼴을 사용합니다.

## 검증

```sh
npm test -- --run
npm run build
npx playwright install chromium --no-shell
npm run test:e2e
npm run test:pages
npm audit
```

- 단위·React 통합 테스트: 계산, 데모 세션, 미입력/빈 데이터, 오류, HTML 텍스트 안전 표시, 관리자·학습 경로와 로컬 저장.
- Playwright: 원본 HTML과 React에 같은 합성 데이터를 넣어 390px·1440px 화면의 표시 내용 및 주요 요소 크기 비교.
- 운영 API·외부 데이터 연결이 CSP로 차단되는지 실제 브라우저에서 확인.
- `test-results/`에 비교 스크린샷, `playwright-report/`에 실행 보고서 생성. `npx playwright show-report`로 확인.
- 테스트는 운영 사이트를 열거나 운영 DB에 요청하지 않습니다.

## 구성

```text
src/
  App.tsx             로그인 모양·데모 진입·탭·브라우저 이동
  Scores.tsx          주간/모의고사·점수 카드·차트 React 컴포넌트
  domain.ts           순수 성적 계산·설정·날짜 정렬
  gateway.ts          데이터 접근 계약과 데모 세션 구현
  data/demo-score.json 명시적 합성 데이터
  styles/             기존 공통/성적 CSS를 기반으로 한 스타일
tests/                단위·컴포넌트 회귀 테스트
e2e/
  fixtures/           원본/React 공통 합성 응답
  legacy/             운영 연결을 제거한 원본 비교 전용 HTML/CSS
  *.spec.ts           브라우저 동작·안전성·레이아웃 비교
docs/                 이전 범위·차이·출처·검증 기록
```

`e2e/legacy`는 테스트 비교용이며 배포 산출물에 포함되지 않습니다. React 앱은 레거시 HTML/스크립트 실행, iframe, `dangerouslySetInnerHTML`에 의존하지 않습니다.

## 실제 서비스 전환 로드맵

**현재는 화면과 업무 흐름을 확인하는 공개 데모다. DB 주소나 API 키만 넣으면 운영 서비스가 되는 상태가 아니다.** 관리자 로컬 데이터와 학생 성적 fixture가 분리되어 있고, 실제 인증·서버 권한 검사가 없다. 아래 항목은 계획이며 아직 연결하지 않았다.

목표 사용자 흐름: **교사가 로그인 → 반/시험을 선택해 점수 저장 → 해당 학생·보호자만 같은 성적을 조회 → 교사가 대상·내용을 확인해 알림 발송 → 발송 결과와 변경 이력을 확인**한다. 단어 학습은 응답 기록·판정 근거·교사 수정까지 서버에 남긴다.

### 1. 운영 전환 전에 확보할 것 — 선행 조건

- [ ] 고객의 운영 전환 승인, 실제 서비스 관리자와 개인정보 처리 책임자 지정.
- [ ] 기존 Supabase의 실제 스키마·RLS·배포 함수·인증·문자 서비스 계약 확인. 저장소의 함수 사본이 운영본과 같다고 가정하지 않는다.
- [ ] 운영과 분리된 테스트 DB/API, 제한된 테스트 계정, 백업·복구 권한 확보.
- [ ] 원본과 데모의 기능 차이를 확인하고 반드시 보존할 업무 규칙 확정. 특히 반 이동/주차 매칭, 재시험 원점수, 동적 시험 항목, 미응시·결측치, 문자 대상 정책.
- [ ] 학부모·학생 연락처의 정확성, 수신자 관계, 개인정보 고지·동의 및 처리위탁/보관 정책 검토. 실제 데이터와 비밀키를 공개 데모·Git·채팅에 넣지 않는다.

이 조건을 확인하기 전에는 운영 DB 연결이나 실제 메시지 발송을 하지 않는다.

### 2. DB/API와 화면 간 데이터 통합 — 필수

- [ ] 기존 DB를 재사용할지 별도 운영 DB로 이전할지 결정하고 데이터 접근 adapter 구현. 프런트엔드 개편 때문에 DB를 무조건 새로 만들지는 않는다.
- [ ] 학생·보호자·반·시험·항목 설정·점수·출결·클리닉·단어/지문·학습 기록을 서버의 동일한 데이터 모델로 통합.
- [ ] `gateway.ts`의 데모 경계와 각 화면의 localStorage 접근을 운영용 API로 대체. **관리자에서 저장한 점수가 학생 성적 화면에 반영되도록 연결**한다.
- [ ] API 입력/응답 런타임 검증, 서버 계산 검증, 트랜잭션, 동시 수정 충돌 처리, 요청 중복 방지, 페이지네이션과 오류 복구 구현.
- [ ] 콘텐츠·시험 버전과 기존 ID 보존. 특히 `그룹|DAY|단어` ID에 연결된 즐겨찾기·오답 기록은 별도 매핑/검증 없이 변경하지 않는다.
- [ ] 실제 자동 변경 이력(누가·언제·무엇을), 서버 백업, 복원 절차 구현. 현재 수동 로컬 스냅샷은 운영 감사 이력을 대체하지 못한다.

완료 기준: 테스트 환경에서 저장→조회→수정→복원을 검증하고, 다른 학생/반 정보가 잘못 섞이지 않으며 새 기기에서도 동일한 기록을 조회한다.

### 3. 실제 로그인·서버 권한 — 필수

- [ ] 관리자/조교와 학생/보호자의 인증 방식을 분리. 관리자 계정별 권한과 필요 시 MFA, 학생-보호자 연결 관계를 관리한다.
- [ ] 이름+전화번호 뒷자리만으로 충분한 인증이 된다고 보지 않는다. 기존 이용 편의와 보안 요구를 검토해 초대·일회용 인증 등 적절한 방식을 결정한다.
- [ ] 서버 세션 또는 검증된 인증 서비스 적용. 현재 localStorage의 데모 표시는 인증으로 전용하지 않는다.
- [ ] API마다 사용자·역할·학생/반 범위를 검사하고 DB RLS와 함께 방어. 관리자 URL을 숨기는 것은 접근 제어가 아니다.
- [ ] 로그아웃·만료·계정 정지·세션 회수, 로그인 시도 제한, CSRF/CORS 및 쿠키 정책 검증.

완료 기준: 로그인하지 않은 호출과 학생 A의 학생 B 조회/수정 요청을 서버가 거절한다. 관리자 화면을 직접 열어도 권한 없이 실제 데이터를 받지 못한다.

### 4. 단어 규칙 채점·AI 채점 연결 — 기능 복원 단계

- [ ] 원본의 품사·어간·유사도·제외 조건·인정 답안 규칙을 먼저 이식하고 고정 회귀 테스트로 비교. 현재 데모의 정답 문자열 비교와 구분한다.
- [ ] 애매한 응답만 서버에서 AI에 전달. 모델 키·프롬프트 관리·요청 제한은 서버에서 수행하고 `VITE_*` 환경 변수에 비밀키를 넣지 않는다.
- [ ] 교재의 해당 단어/뜻/품사/문맥·채점 정책을 판정 입력으로 사용. 외부 근거 검색(RAG)이 필요한 경우에만 검색 단계를 추가한다.
- [ ] 원래 답안, 판정 방식(규칙/AI/교사), 사용 근거, 모델·프롬프트 버전, 교사 정정 기록을 보존한다.
- [ ] 실패·시간 초과·모호한 답안은 보류/교사 확인으로 넘긴다. AI 인정 답안을 모든 학생에게 자동 공유하지 않고 별도 승인한다.
- [ ] 교사가 확정한 평가 세트로 오인정·오거절률, 품사/부정/동의어 사례, 지연시간·비용을 측정하고 허용 기준 합의.
- [ ] 학생 이름·연락처 등 불필요한 개인정보를 AI 업체로 보내지 않으며 업체의 데이터 보관/이용 정책을 검토한다.

AI는 성적 조회 서비스 출시의 필수 조건은 아니다. 먼저 DB·로그인·규칙 채점까지 운영하고 AI를 단계적으로 붙일 수 있다. AI 비용은 선택 모델·입출력 토큰·호출률·캐시에 따라 달라지므로 메시지 발송비와 별도로 산정한다.

### 5. 알림 발송 — 서버 구현 및 운영 승인 필요

- [ ] 발송 채널(SMS/LMS 또는 카카오 알림톡), 발송 대상(학생/보호자), 내용·빈도·예산을 고객과 확정.
- [ ] 브라우저는 발송 요청만 하고, 서버가 권한·수신자·템플릿·변수를 검증한 뒤 업체 API 호출. 발송용 비밀키는 서버에만 저장.
- [ ] 교사 미리보기/최종 승인, 예약·취소 정책, 수신자 중복 제거, 발송 요청별 멱등 키와 큐 구현.
- [ ] API 접수와 최종 전송 성공을 구분. 웹훅 검증 또는 결과 조회로 성공/실패/대체 발송을 기록하고 재시도 중복 과금을 방지.
- [ ] 테스트 환경은 수신번호 허용 목록과 기본 발송 차단을 적용. 소수 승인된 번호로 검증한 후 일별 한도·잔액 경고·긴급 발송 중지 기능을 켠다.

### 6. 배포·데이터 이전·운영 검증 — 출시 조건

- [ ] 공개 데모와 운영 서비스의 환경·도메인·DB·키를 분리. GitHub Pages에는 비밀키나 실제 학생 데이터가 담긴 정적 파일을 배포하지 않는다.
- [ ] Pages는 현재 프런트엔드 배포용이다. 운영 API/인증/AI/발송은 별도 서버·Edge Function 등에서 실행하고, 가능하면 같은 출처의 `/api`를 제공하는 배포 구성을 검토한다.
- [ ] 현재 `connect-src 'none'`은 데모 안전장치다. 운영 빌드에서만 승인된 API 주소를 허용하고 CORS·세션 쿠키·HTTPS를 함께 검증한다. 허용 범위를 무제한으로 풀지 않는다.
- [ ] 기존 데이터 백업 → 테스트 환경 이전 → 건수/ID/성적/권한 대조 → 제한된 반에서 시범 운영 → 전환 승인 순서로 진행.
- [ ] 배포 실패·데이터 오류 시 롤백 기준, 복구 리허설, 개인정보 로그 마스킹, 장애 알림, 비용 모니터링과 담당자 인수인계 문서 마련.
- [ ] 실제 로그인/권한 → 관리자 저장 → 학생 조회 → 채점 → 승인 발송 → 결과 확인을 테스트 환경에서 종단 간 검증.

**권장 순서:** 기존 운영 계약 확인 → 테스트 DB/API → 로그인·권한 → 관리자/학생 데이터 통합 → 규칙 채점 복원 → 승인형 알림 발송 → 제한된 운영 전환 → AI 채점 고도화. OCR·RAG·클리닉 에이전트는 그 이후 확장 과제다.

## 카카오 알림톡 도입 가능 여부와 비용

확인일: **2026-10-25**. 아래 가격은 SOLAPI의 공개 표준 단가를 이용한 비교 예시이며 계약 확정 견적이 아니다. 업체별 서비스·단가·계약 조건이 다르므로 최종 가입 시 재확인한다.[1][2]

### 문자 대신 알림톡을 사용할 수 있는가?

**가능하다. 다만 자유문자 발송 버튼을 그대로 대체하는 방식은 아니다.** 알림톡은 기존 거래/계약 관계에서 필요한 정보성 메시지를 공식 딜러사를 통해 보내는 서비스이며, 승인된 템플릿을 사용해야 한다.[2][3]

이 프로젝트에서는 **기존 수강생의 성적 게시 알림, 확정된 클리닉 일정, 출결·과제 관련 안내**를 도입 후보로 삼을 수 있다. 이는 적용 제안이지 해당 문구의 심사 통과를 보장하는 것은 아니다. 최종 내용·수신자 관계는 딜러사와 카카오 심사로 확인한다. 신규 수강생 모집·할인 홍보 등 광고 문구는 정보성 알림톡과 분리한다.[2][3]

- 카카오 채널을 친구로 추가하지 않은 수신자에게도 승인된 정보성 알림톡을 보낼 수 있다. 이것이 모든 목적의 무동의 발송을 허용한다는 뜻은 아니다.[2][3]
- 비즈니스 채널 생성/연동 후 템플릿을 등록·검수받아야 한다. 채널 연동 전 사전 템플릿 등록은 불가하다는 SOLAPI 안내가 있다.[4]
- 이름·날짜·시간 등은 승인 템플릿의 `#{변수명}`으로 치환하고, 웹 링크 버튼을 붙일 수 있다.[3]
- 교사가 매번 완전히 다른 자유문을 쓰거나 AI가 새 안내문을 만드는 방식을 그대로 발송하지 않는다. 승인된 구조와 변수 범위를 유지하고 새 목적의 문구는 새 템플릿으로 검토한다.[3][4]
- 권장 설계: 성적 전체를 알림 본문에 나열하기보다 “성적이 등록되었습니다”와 **로그인 후 본인 정보만 보이는 링크**를 보낸다. 현재 공개 데모 링크를 실제 성적 조회 링크로 사용하지 않는다.

### 준비·구현 체크리스트

1. 학원 소유의 비즈니스 채널과 관리자 권한, 선택 딜러사 계정/계약을 확인한다.[2][4]
2. 성적 게시·클리닉 일정·출결 안내 등을 분리해 템플릿을 신청한다. SOLAPI는 검수에 보통 영업일 1~3일을 안내하지만 정확한 기간은 보장하지 않는다.[4]
3. 서버에 채널/템플릿 ID, 승인된 변수 목록과 유효성 검사를 등록한다. 결제·API 자격증명은 서버 비밀 저장소에서 관리한다.
4. 실패 시 SMS/LMS로 대체할지 명시적으로 정한다. SOLAPI는 기본적으로 대체 발송을 안내하므로, 테스트 단계에서는 비활성화 여부를 확인하고 운영에서는 비용 상한과 함께 활성화한다. 문자 대체에는 등록된 발신번호가 필요하다.[3][4]
5. 승인된 테스트 수신번호로 알림톡 성공·실패·대체 발송·중복 요청을 검증한 후 운영 전환한다.

### 공개 표준 단가 비교

SOLAPI 웹/API 직접 연동 표준 단가. 국내 VAT 10%를 가정한 포함 가격은 아래 단가에 1.1을 곱한 계산값이다.[1]

| 채널 | 건당 VAT 별도 | 건당 VAT 포함 계산값 | 비고 |
| --- | ---: | ---: | --- |
| 카카오 알림톡 | 13원 | 14.3원 | 승인 템플릿 기반 |
| 단문 SMS | 18원 | 19.8원 | EUC-KR 90바이트 |
| 장문 LMS | 45원 | 49.5원 | EUC-KR 2,000바이트 |

위 단가는 공식 공개 요금표 기준이다. 기본 월 사용료와 일반 API 사용료는 무료라고 안내되어 있으나, 대량 호출·추가 웹훅·앱/별도 구독 상품은 추가 비용이 있을 수 있다. 발송량 할인도 있으므로 계약 때 확인한다.[1]

### 월 예상 비용 예시 — 실사용량 아님

가정: 학생당 보호자 **1명에게 월 4건**, 모두 알림톡으로 성공, 건당 13원, 할인·문자 대체 없음. 아래 인원은 비용 설명을 위한 가상 시나리오이며 실제 학원 학생 수가 아니다.[1]

| 대상 학생 수 | 월 발송 건수 | VAT 별도 | VAT 포함 |
| --- | ---: | ---: | ---: |
| 100명 | 400건 | 5,200원 | 5,720원 |
| 300명 | 1,200건 | 15,600원 | 17,160원 |
| 500명 | 2,000건 | 26,000원 | 28,600원 |

예를 들어 300명에게 월 8건이면 2,400건으로 VAT 포함 **34,320원**이다. 보호자 2명 또는 학생+보호자에게 각각 보내면 수신번호별 발송 건수를 다시 계산해야 한다.[1]

예산 산식: `수신번호 수 × 월 발송 횟수 × 계약 단가 × VAT 계수`.

실제 청구는 알림톡과 SMS/LMS 등 **각 채널의 과금 대상 건수**를 기준으로 산정한다. 실패 건의 환급/과금 처리와 재시도 정책은 계약 확인 전 단정하지 않는다. 대체 발송이 켜져 있으면 전부 알림톡 단가로 계산하면 안 된다.[1][3][4]

**위 금액에 포함되지 않는 것:** DB·서버·저장소·도메인·모니터링, AI 호출, 최초 개발·데이터 이전·유지보수 비용. 메시지 비용만으로 전체 운영비를 판단하지 않는다.

### 이 프로젝트의 권장 선택

- 우선 알림톡 **성적 게시 / 클리닉 일정** 두 템플릿을 시범 도입하고, 기존 문자 발송은 실패 시 대체 또는 알림톡에 맞지 않는 업무 용도로 검토한다.
- 비용 예산의 출발점은 위 표처럼 잡되, 실제 수신자 수·빈도·실패율·문자 길이를 확인해 재산정한다.
- 아직 채널 가입·템플릿 심사·실제 발송을 진행한 것은 아니다. 이 README 변경은 운영 전환 계획과 비용 조사 기록이다.

## 관리자 백엔드 (backend/, Spring Boot · 읽기 전용)

상담 준비 탭의 "실제 DB" 구역이 쓰는 API. 읽기 전용 DB 계정으로만 붙는다.

`.env.local`(gitignore됨)에 필요한 값:

| 변수 | 용도 | 없으면 |
|---|---|---|
| `DB_URL` `DB_USER` `DB_PASSWORD` | 읽기 전용 DB 계정 | 기동 실패 |
| `ADMIN_PASSWORD` | 관리자 로그인 비밀번호 | `/api/admin/**` 전부 503 |
| `ADMIN_SESSION_SECRET` | 로그인 쿠키 서명, 32자 이상 (`openssl rand -hex 32`) | `/api/admin/**` 전부 503 |
| `GEMINI_API_KEY` | 상담 질문 생성 | 질문만 503, 카드는 동작 |

```
cd backend
set -a; . ../.env.local; set +a
./mvnw spring-boot:run                  # 127.0.0.1:8080
```

다른 터미널에서 `npm run dev` → 관리자 → 상담 준비. 개발 서버가 `/api/admin`을 8080으로 넘긴다.
로그인은 HttpOnly 쿠키(12시간), 같은 IP에서 5회 실패하면 10분 잠금.

배포: AWS Lambda(SnapStart) — `infra/README.md` 참고.
